# GitHub Actions with a Self-Hosted Runner

## 1. Objective

Set up a free CI/CD pipeline for the RailRush frontend using GitHub Actions and a local Ubuntu VM created with Multipass.

Instead of using a cloud-hosted deployment server, I used my MacBook as the host machine and an Ubuntu VM as the deployment server.

**What this pipeline achieves:**

1. Detects a push to the `main` branch.
2. Executes the GitHub Actions workflow on my Ubuntu VM.
3. Pulls the latest repository code.
4. Installs frontend dependencies.
5. Builds the React application.
6. Deploys the production build to Nginx.

This is a learning setup. The VM is accessible only while the MacBook and VM are running.

## 2. Architecture

### Hosted runner vs self-hosted runner

**GitHub-hosted runner:**

* GitHub provisions and manages the machine.
* The workflow executes on GitHub's infrastructure.
* A hosted runner cannot directly access a private IP address such as my local VM's `192.168.252.2`.

**Self-hosted runner:**

* I provide and manage the machine.
* GitHub assigns workflow jobs to my registered machine.
* The workflow commands execute on that machine.
* I installed the runner inside my Ubuntu Multipass VM.

## 3. Creating the Ubuntu VM

Created the VM from the Mac terminal:

```
multipass launch --name devops-vm --cpus 2 --memory 2G --disk 10G
```

Enter the VM:

```
multipass shell devops-vm
```

Useful commands:

```
whoami
pwd
uname -m
```

The VM uses Ubuntu ARM64 (`aarch64`).

## 4. Connecting Ubuntu to GitHub using SSH

I generated a dedicated SSH deploy key inside Ubuntu:

```
ssh-keygen -t ed25519 -C "railrush-devops-vm" -f ~/.ssh/railrush_github
```

This generates:

* `railrush_github` — private key.
* `railrush_github.pub` — public key.

I added the public key to:

GitHub → Repository → Settings → Deploy keys.

The key was configured with read-only access.

### SSH configuration

Since SSH did not automatically select the custom key, I configured an alias in:

`~/.ssh/config`

```
Host github-railrush
    HostName github.com
    User git
    IdentityFile ~/.ssh/railrush_github
    IdentitiesOnly yes
```

Set permissions:

```
chmod 700 ~/.ssh
chmod 600 ~/.ssh/config
chmod 600 ~/.ssh/railrush_github
```

Clone the repository:

```
git clone git@github-railrush:Yashika-Agrawal/RailRush.git
```

Repository location:

`/home/ubuntu/RailRush`

**Important:** The private key must never be committed to GitHub.

## 5. Installing Node.js using NVM

Installed NVM as a user-level tool:

```
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash
source ~/.bashrc
```

Install Node.js 22:

```
nvm install 22
nvm alias default 22
```

Verify:

```
node -v
npm -v
```

### Understanding installation locations


| Component             | Location                           |
| --------------------- | ---------------------------------- |
| NVM                   | `~/.nvm`                           |
| Node.js               | `~/.nvm/versions/node/`            |
| Repository            | `~/RailRush`                       |
| Frontend dependencies | `~/RailRush/frontend/node_modules` |
| Production build      | `~/RailRush/frontend/dist`         |

NVM is installed for the Ubuntu user, not separately inside each project.

### Install dependencies and build

```
cd ~/RailRush/frontend
npm ci
npm run build
```

**Why ** `npm ci`**?**

* Installs dependencies using `package-lock.json`.
* Provides a predictable dependency installation.
* Removes the existing `node_modules` before installation.
* Is suitable for automated CI/CD pipelines.

**Important:** `npm run build` uses project-local binaries from `node_modules/.bin`, so it uses the versions specified by the project rather than relying on globally installed TypeScript or Vite.

Select:

* Operating system: Linux
* Architecture: ARM64

Follow the commands generated by GitHub to download and configure the runner.

I installed it at:

`/home/ubuntu/actions-runner`

`devops-vm`

GitHub provides a temporary registration token during setup. It should not be stored in the repository or committed to source control.

```

```

Expected output:


## 7. Troubleshooting: Runner authentication failure due to clock drift

### Problem

The runner connected to GitHub but failed to create a session.

The diagnostic logs reported an expired OAuth token.

### Investigation

Checked Ubuntu time:

```
date -u
timedatectl status
```

Compared it with GitHub's server time:

```
curl -sI https://api.github.com | grep -i '^date:'
```

The VM clock was significantly behind GitHub's server time.

### Identifying the time synchronization service

```
systemctl status chrony --no-pager
```

Found that Chrony was running.

Checked synchronization:

```
chronyc tracking
chronyc sources -v
```

The tracking output showed that the system clock was thousands of seconds behind NTP time.

### Fix

```
sudo chronyc makestep
```

`makestep` instructs Chrony to correct the system clock immediately instead of gradually adjusting it.

Verified:

```
chronyc tracking
date -u
```

The system time was then aligned with the NTP source.

**Learning:** A service being active does not necessarily mean that the system clock is synchronized. Always inspect the actual synchronization status.

## 8. Running the runner as a system service

### Why?

Running `./run.sh` manually requires keeping the terminal session alive.

For a persistent runner, I configured it as a Linux system service.

Stop the manually running runner using `Ctrl + C`.

From the runner directory:

```
sudo ./svc.sh install
sudo ./svc.sh start
```

Check status:

```
sudo ./svc.sh status
```

### Benefits

* Runs in the background.
* Does not depend on an open terminal.
* Starts automatically when Ubuntu boots.
* Can be managed through systemd.

Useful commands:

```
sudo ./svc.sh status
sudo ./svc.sh stop
sudo ./svc.sh start
```

The runner service runs under its configured Linux account. In this setup, that is the `ubuntu` user.

**Important:** The MacBook must remain powered on and the Multipass VM must be running. A system service cannot keep a powered-off VM alive.

## 9. GitHub Actions workflow

Workflow file location:

`.github/workflows/deploy.yml`

```
name: RailRush Deployment

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: self-hosted

    steps:
      - name: Pull latest code
        run: |
          cd /home/ubuntu/RailRush
          git pull

      - name: Install dependencies
        run: |
          cd /home/ubuntu/RailRush/frontend
          npm ci

      - name: Build frontend
        run: |
          cd /home/ubuntu/RailRush/frontend
          npm run build

      - name: Deploy to Nginx
        run: |
          sudo cp -r /home/ubuntu/RailRush/frontend/dist/. /var/www/railrush/
          sudo systemctl reload nginx
```

### Understanding the YAML

`name`

Defines the workflow name displayed in the GitHub Actions tab.

`on`

Defines the event that triggers the workflow.

```
on:
  push:
    branches:
      - main
```

This triggers the workflow when code is pushed to `main`.

`jobs`

A workflow contains one or more jobs.

`runs-on: self-hosted`

Tells GitHub to assign the job to an available self-hosted runner.

`steps`

Defines the sequence of operations executed by the job.

`run`

Executes shell commands on the machine where the runner is running.

### Important execution concept

In our current setup:

* `runs-on: self-hosted` selects the Ubuntu VM.
* `run:` executes commands inside that Ubuntu VM.
* `git pull` updates the repository clone on the VM.
* `npm ci` installs dependencies on the VM.
* `npm run build` builds the application on the VM.
* `sudo cp` copies the build into the Nginx document root.

There is no separate SSH action in this workflow because the runner itself is already on the target server.

## 10. Passwordless sudo

The workflow needs elevated permissions to copy files into `/var/www/railrush` and reload Nginx.

Checked whether the Ubuntu user can run sudo commands without an interactive password:

```
sudo -n true
echo $?
```

Output:

```
0
```

Exit code `0` indicates that the command succeeded without prompting for a password.

**Security note:** Passwordless sudo should be restricted carefully. In production, prefer narrowly scoped permissions for the specific deployment operations rather than granting unrestricted passwordless sudo.

## 11. Security considerations

Self-hosted runners execute workflow code on my own machine.

Therefore:

* Never expose private SSH keys or registration tokens in workflow files.
* Do not execute untrusted pull-request code on a privileged self-hosted runner.
* Restrict who can push to the deployment branch.
* Use least-privilege access for deployment.
* Keep the runner and its dependencies updated.
* Avoid exposing unnecessary ports on the VM.

For this learning project, the workflow is triggered only by pushes to `main`.

## 12. Current implementation limitations and future improvements

The current workflow is a simple deployment pipeline, not a complete production-grade CI/CD setup.

Possible improvements:

1. Add a separate CI job for linting and testing.
2. Use `actions/checkout` or another controlled checkout strategy instead of relying on `git pull`.
3. Make Node.js/NVM available reliably to the runner's non-interactive service environment.
4. Add deployment rollback.
5. Add deployment health checks.
6. Separate build and deployment jobs.
7. Introduce environment protection and approvals.
8. Use more restrictive deployment permissions.

**Important NVM consideration:** A system service may not load the interactive shell configuration in `.bashrc`. If `npm` is not found during a workflow, inspect the runner service's `PATH` and configure access to the installed Node.js binaries explicitly.

## 13. Quick questions

**Q: What is a self-hosted GitHub Actions runner?**

A machine that I manage and register with GitHub Actions to execute workflow jobs.

**Q: Why did you use a self-hosted runner?**

My Ubuntu VM was running locally on a private network. A GitHub-hosted runner could not directly reach that private IP. A self-hosted runner allowed the workflow to execute directly on the target VM.

**Q: Does the runner need to run in a terminal?**

No. It can be installed as a system service and managed using systemd.

**Q: What is Chrony?**

Chrony is an implementation of NTP used to synchronize a system clock with external time sources.

**Q: Why did the runner fail authentication?**

The diagnostic logs reported expired OAuth tokens. Investigation revealed substantial clock drift on the Ubuntu VM. Correcting the clock using Chrony resolved the issue.

**Q: What is the difference between ** `run` ** and ** `uses`**?**

`run` executes shell commands. `uses` invokes a GitHub Action.

**Q: What happens if the MacBook shuts down?**

The Multipass VM stops, making the self-hosted runner unavailable until the VM starts again.
